TaskPilot Repo Integration: Key Design Question

I created TaskPilot to solve a coordination problem within our development team. When multiple developers use AI agents on different machines, those agents often work in different directions because they do not know what the other agents have already done, decided, or discovered.

TaskPilot solves this by sharing task context between agents in real time. A team member should only need to open their preferred AI agent, and TaskPilot should automatically provide the latest context related to the task.

In the current version, developers do not need to push code, commit changes, manually save progress, or ask another team member to publish context. The context is captured and shared automatically, making the process smooth and frictionless.

However, while adding repository-level integration, an important design question arises:

Should TaskPilot’s context synchronization depend on Git commits or pushes?

Consider this scenario:

Developer 1 works on a task for two days but does not commit or push the changes.
During the same period, Developer 2 is working on the same or a related task from another machine.
Developer 2’s agent needs to understand Developer 1’s current progress, decisions, modified files, problems encountered, and intended next steps.

In this situation, will repo-enabled TaskPilot automatically share Developer 1’s live working context with Developer 2’s agent, even though no code has been committed or pushed?

Or will TaskPilot only update the shared context after a Git commit or push?

The core purpose of TaskPilot is to remove this dependency. If context synchronization relies only on Git commits or pushes, the other agents may continue working with outdated information for hours or even days.

"The shared Claude conversation is about how TaskPilot should automatically capture developer context and inject that context into coding agents, especially when multiple people or agents work in parallel on different machines.

The conversation starts with your product framing. You explain that you built TaskPilot because agents on different machines were drifting in different directions with no shared awareness of each other’s work. Your goal is that when a team member opens their agent, the relevant task context is already there automatically, without asking anyone to push code, save state, or manually publish context. You then raise the key repo-feature question: if Developer 1 works locally for two days without committing, and Developer 2 works at the same time, can the repo feature still automatically surface Developer 1’s in-progress context to Developer 2, or is there an unavoidable dependency on commits and pushes?

Claude’s first substantive answer is that this is a real architecture question, and the answer depends on separating two different problems: capture and injection. Capture means observing what a developer is doing locally before commit. Injection means getting that context in front of the next agent before or while it reasons. Claude says capture is the easier half and should not depend on terminals, typed commands, or git commits. The recommendation is a long-running OS-level daemon installed once per machine as a login/background service. That daemon should watch repo activity continuously using native filesystem watchers like `inotify`, `FSEvents`, or `ReadDirectoryChangesW`, with `git status --porcelain` or similar as a fallback. That gives you zero dependency on commit or push for observing work in progress.

Then Claude moves to injection, which it describes as harder, because there are only a few reliable channels to get context into an agent automatically. The first proposed mechanism is session lifecycle hooks. Claude says Claude Code, Codex, and Gemini CLI all expose some form of session-start hook. In that model, a repo-scoped config runs a shell command when an agent session starts or resumes, and that command prints TaskPilot context to stdout, which becomes a real message in the conversation. The rough example given is a `SessionStart` hook that runs something like `taskpilot context render --format=claude-context`. Claude emphasizes that this is stronger than hoping the model reads a file on its own, because the hook output is injected directly into the conversation.

The second mechanism is auto-loaded repo instruction files such as `CLAUDE.md`, `AGENTS.md`, and `GEMINI.md`. Claude treats this as a very important cross-agent layer. The key idea is not to write those files once and forget them, but to have the daemon continuously rewrite a bounded “live TaskPilot context” section inside them whenever something meaningful changes, like locks, blockers, task state, or fresh work. Because many agents automatically read these files at session start, this becomes a universal low-friction delivery channel that works even when hooks or MCP are not available. Claude also warns that this live section must stay short and be overwritten in place instead of growing, otherwise it quietly consumes prompt budget.

The third mechanism is MCP. Claude says repo-scoped MCP configuration should be committed so all developers get the same server/tool setup while keeping auth local in environment variables. MCP is framed as the deep-query layer rather than the primary guaranteed-delivery layer. The kinds of tools mentioned are things like `get_active_overlaps` and `record_session_context`. Claude’s reasoning is that MCP is great for richer on-demand context, but should not be the only path for the core fact that “someone else is already working here,” because tool invocation is still probabilistic.

Claude then distills this into a one-time setup story. In its first version of the recommendation, there are only two setup actions: install the daemon once per machine so it runs forever, and run something like `taskpilot enable` once per repo so it writes hook config, MCP config, and starts the live context file behavior. After that, the developer should not need to type anything special. The daemon runs continuously, hooks fire automatically on each session start, and the context file is always current.

That leads into the second major part of the conversation, where you propose your own layered delivery architecture. Your plan is: primary channel should be an agent shim for CLI agents, secondary should be MCP for GUI or desktop agents, baseline should be repo instruction files, and fallback should be daemon conflict warnings. In your shim model, the developer still types `codex`, but TaskPilot intercepts that command and really runs something like `taskpilot agent exec codex`. The shim would detect the repo, load task context from the TaskPilot server, inspect overlaps and changed files, find or create the current task/session, build startup context, launch the real agent with that injected context, and then continue syncing heartbeats, locks, and progress. For GUI agents, you suggest MCP tools. For the baseline, you suggest `AGENTS.md` instructions telling the agent to call TaskPilot before planning or editing. And if none of those work, the daemon should still detect overlapping file edits and raise warnings, record conflicts, or notify the dashboard. You also explicitly state an honest product constraint: you cannot guarantee automatic injection into every arbitrary agent unless it is launched through a shim, reads repo instructions, or supports MCP. So your guarantee hierarchy is capture always, injection guaranteed for configured CLI shims, strong for MCP-capable GUI agents, and best-effort for instruction-only agents.

Claude’s final answer says the two plans mostly converge. It says both architectures share the same skeleton: always-on daemon underneath, some mechanism for CLI agents, MCP for GUI agents, and repo instruction files as a baseline. The real disagreement is not the whole architecture, but specifically what should occupy the CLI slot: shims or hooks.

Claude then argues in detail that hooks are better than shims as the primary CLI mechanism. The reasoning is multi-part. First, even if a shim intercepts `codex`, it still needs some way to inject context into the model. Once you unpack it, the shim only has a few options: pass an initial prompt argument, rewrite `AGENTS.md` before launch, or rely on hooks anyway. That means the shim is not a totally separate primitive; in many cases it is just another front door to mechanisms you already need. Claude says the only distinct value of the shim is the literal prefilled prompt route, but that is tool-specific, fragile to CLI flag changes, and visually dumps a large context block into the transcript as if the user typed it.

Second, Claude argues that shims are less reliable across launch contexts. They depend on PATH manipulation, shell rc files, shell type, IDE-integrated terminals, and how the process was launched. That creates the exact sort of “fresh shell / wrong shell / bypassed wrapper” failure mode your product is trying to eliminate. Hooks, by contrast, are agent-native. If the agent itself reads project config on startup, the mechanism works regardless of how the process was launched.

Third, Claude points out the blast radius issue. With a shim, TaskPilot sits in the critical launch path. If the shim hangs or the TaskPilot server is unreachable, the agent itself may not start unless you very carefully design fail-open behavior. Hooks are a side channel the vendor already designed for injecting development context, so you inherit more standard behavior and less custom launch complexity.

Fourth, Claude says shims add engineering surface area. Supporting three CLIs well means handling shell differences, locating real binaries so you do not recurse into yourself, and revalidating behavior every time vendors change packaging or flags. By contrast, hooks are just small config blocks written once by something like `taskpilot enable`.

So Claude’s final decision is clear: for Codex, Claude Code, and Gemini CLI, session-start hooks should be the primary mechanism for CLI context delivery, not shims. Shims should remain a long-tail fallback only for future or niche agents that support neither hooks nor MCP nor auto-loaded repo files. At the same time, Claude strengthens the role of live repo instruction files. It says not to treat `AGENTS.md` as a weak static baseline. Instead, make the daemon continuously rewrite a bounded live context section there, because that turns the most universal cross-agent file into a very strong delivery mechanism. In other words, hooks become the top mechanism for CLI agents, but live-rendered repo instruction files become the universal floor across all agents.

The final recommended architecture, as Claude states it, is:

Primary for CLI agents: session lifecycle hooks like `SessionStart`.
Strong universal floor: continuously live-rendered `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`.
Secondary for GUI/desktop agents and deeper queries: MCP repo-context tools.
Always-on safety net: daemon-based capture and conflict warnings.
Long-tail fallback: shims, only for tools that genuinely lack hooks, MCP, and context-file support.

Claude also recommends reordering the build plan accordingly:
1. Build the daemon for live capture using filesystem watching plus git diff.
2. Build the server-side task/context resolution API.
3. Add hook config for Claude Code, Codex, and Gemini CLI.
4. Add live-rendered repo context files written by the daemon.
5. Add MCP repo-context tools for GUI agents.
6. Build shims later only if a target tool truly needs them.

A few implementation cautions are also included. The daemon should debounce writes so it does not regenerate context on every keystroke. The live context section in repo files should stay short and be overwritten rather than appended. Hook trust prompts, especially in tools like Codex, are acceptable friction because they are security features rather than product failure. And the honest product truth remains: automatic capture can be made unconditional with a daemon, but automatic injection is only guaranteed where the target agent exposes a supported channel such as hooks, repo instruction loading, or MCP.

So the overall conclusion of the shared conversation is not that your idea was wrong. Claude basically validates your layered model and your honesty about guarantees. The main correction is strategic: don’t put shims at the center of the CLI design when hooks already exist. Use hooks as the primary CLI mechanism, make the daemon continuously maintain live repo context files as the universal layer, use MCP for richer desktop-agent integration, and keep shims only as a fallback adapter for unsupported agents. A few concrete ideas, mostly around how the writer itself works rather than anything fancier.

The trick to making the merge invisible is patching the JSON surgically instead of round-tripping it through a full parse-and-remarshal. If you unmarshal a developer's `.claude/settings.json` into a generic struct and write it back out, Go will reformat whitespace, reorder map keys alphabetically, and produce a noisy diff even though you only meant to touch one array. A library like `tidwall/sjson` (paired with `gjson` for reading) lets you set a value at a specific path, `hooks.SessionStart.-1`, directly on the raw bytes, leaving every other byte of the file untouched. That's the difference between a one-line diff a teammate glances past in review and a wall of reformatting noise that makes them suspicious of what `taskpilot enable` actually did.

For idempotency, don't rely on a tool-specific `name` field, since Claude Code's hook entries don't reliably have one. Match on the command path instead: you already know `taskpilot enable` always points the command at the same deterministic script, `.taskpilot/hooks/claude-session-start.sh`, so before writing, scan existing `hooks.SessionStart` entries with `gjson` for one whose command matches that path. Found it: update in place if anything changed, otherwise skip the write entirely. Not found: append. That makes `enable` safe to run a hundred times and a no-op on the 99 reruns where nothing actually changed, which also avoids spurious mtime/diff churn if someone runs it out of habit.

Wrap the actual file write in something crash-safe: write to a temp file in the same directory, fsync, then atomic rename over the original, and keep a one-time `.bak` of anything that wasn't created by TaskPilot before you touch it for the first time. These are config files that, if half-written, can break the developer's whole Claude Code or Codex session, so it's worth the few extra lines.

Architecturally, since all three tools converge on nearly the same shape (`hooks.SessionStart[].hooks[].{type, command}`), build one shared Go type for "a session-start hook entry" plus the merge/idempotency/atomic-write logic once, and let each tool be a thin adapter that only knows its file path, its quirks (Codex's feature flag, Gemini's stricter output contract), and nothing else. That keeps the risky part of the code, the part that touches a developer's existing config, tested in exactly one place instead of three.

The biggest lever for "seamless" though isn't in the writer at all, it's deciding these files get committed. `.claude/settings.json` and `.codex/hooks.json` contain no secrets, just a path to a script that's identical on every clone, so there's no reason to keep them local-only. If one developer runs `taskpilot enable` once and commits the result, every teammate gets the hook wired up the moment they `git pull`, without ever typing `taskpilot enable` themselves. That turns "seamless" from a property of your code into a property of your team's normal workflow.

And have `enable` print exactly what it changed, in plain language, "registered a Claude Code session-start hook in .claude/settings.json," "registered a Codex hook, you'll see a one-time approval prompt the first time you open Codex here." Seamless doesn't have to mean silent, just that the developer never has to do anything beyond reading one line of output.
