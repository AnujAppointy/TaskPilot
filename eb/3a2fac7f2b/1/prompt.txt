The child agent is failing because the MCP server process is not necessarily using the same TaskPilot config/server address as the parent CLI.
The core mismatch is:
taskpilot run passes TASKPILOT_SERVER, TASKPILOT_ACTOR_ID, and related env vars into the child agent process.
But taskpilot mcp serve does not use TASKPILOT_SERVER for its API calls.
MCP tool calls go through doRequest(), which calls loadConfig().
loadConfig() reads only TASKPILOT_CONFIG or $HOME/.taskpilot/config.json.
If that config is missing or different inside the child/Codex MCP environment, TaskPilot falls back to http://127.0.0.1:8080.
So the server can be live and healthy, but the MCP process is probably trying the wrong address, commonly:
http://127.0.0.1:8080
That breaks if the real server is on another port, another host/LAN IP, or if 127.0.0.1 inside the child environment points to the child sandbox rather than the host machine.
There is one more likely issue: the Codex MCP config currently registers:
command = "taskpilot"
args = ["mcp", "serve"]
but it does not set TASKPILOT_CONFIG or TASKPILOT_SERVER for that MCP process. So Codex may launch MCP with a different HOME, different config path, or even an older globally installed taskpilot binary from PATH.
In short: the server is healthy, but the MCP subprocess is not inheriting or honoring the same connection context.
The clean fix is to do both:
Make doRequest() honor env overrides like TASKPILOT_SERVER, TASKPILOT_ACTOR_ID, and TASKPILOT_ACTOR_SECRET.
When writing Codex MCP config, include TASKPILOT_CONFIG=<current config path> so taskpilot mcp serve reads the same config as the CLI.
Quick checks:
which taskpilot
echo $TASKPILOT_CONFIG
taskpilot config show
If the child/MCP environment is isolated, avoid 127.0.0.1 and configure TaskPilot with a host/LAN-reachable server URL instead."  now what you think
